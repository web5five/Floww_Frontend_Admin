## Implemented / 구현

`/dashboard` is the post-ADMIN-login and root destination. It uses the existing native Floww mark and turns the reference's desktop sidebar, four metric cards, distribution bar, recent list, selected-task evidence panel, policy outcomes and activity into responsive HTML/CSS. Mobile uses a keyboard-operable navigation drawer and settings dialog. Overview, Tasks, Audit trail and Settings controls all reach working destinations; audit list/detail navigation, filters and pagination remain. The reference's illustrative person/avatar, names, dates, amounts and events were **not** copied into product data.

The dashboard makes five bounded count requests (`limit=1` unfiltered, `AWAITING_APPROVAL`, `ACTIVE`, `EXECUTING`, `COMPLETED`) plus one first-page task request (`limit=5`). It reads each endpoint's `total`; the number of returned rows is never treated as a global count. In progress is `ACTIVE + EXECUTING`; Other is calculated only when all count reads succeed and reconcile with the total. Parallel reads can observe different database moments, so the UI shows check time, a separate-read note and explicit partial/inconsistent states. Recent rows are the first five by **creation** order, not a global latest-event feed. Only a selected Task triggers detail, first event page (`limit=50`, five shown here) and account reads. Selection changes abort prior reads and reject stale generations.

`src/lib/dashboard.ts` formats exact decimal base-unit strings with `BigInt` and known token decimals; the raw base-unit amount and source (selected attempt or TaskAccount) remain visible. Null decimals show base units only. Selected policy, approval, payment and fulfillment steps use separate recorded evidence: DENY does not complete downstream steps; payment requires a verified operation, timestamp, transaction hash and an approved allowed attempt; fulfillment additionally requires completed Task/account and its own timestamp/hash. UNKNOWN remains unknown. No global payment sum, revenue, model tokens or model cost is displayed because the Admin API does not expose them. Task `COMPLETED` is the persisted product state, not a claim of physical delivery.

The F038 locale correction is included: a validated language cookie drives initial HTML language and metadata; browser local storage stays in sync, with a prepaint concealment path for an older local-storage-only preference. Known policy, event, state and reason codes have Korean/English display labels while canonical codes remain secondary technical evidence and are never changed in API requests. Existing `/audit` list/detail now show a translated `/login` recovery link on 401, including event pagination errors. No session role, cookie authority, backend schema or payment path changed in the UI commit.

Independent F044 review found that a selected detail/event/account 401 could occur after overview totals succeeded. The dashboard now treats a selected request's 401/403 as an access state, hides stale selected evidence, and offers `/login` recovery for 401. A selection-only 401/403 browser fixture verifies this path.

At the coordinator's direction, the reviewed separate Admin BFF commit was cherry-picked after the UI commit. It extends audit GET upstream timeout from 10 to 20 seconds, declares `maxDuration=30` on four audit routes and adds a 10.5-second delayed-upstream regression. It leaves sign-in timeout, HttpOnly ADMIN cookie, no-store/redirect refusal, route validation and GET-only behavior intact. This is a local combined source change awaiting publication.
